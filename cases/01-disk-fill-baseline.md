# 案例 01 · 磁盘被写满：建立基线

> 例：「磁盘还有空间但写不进去」，不要写「inode 用尽」
>
> 在动手排查真正的故障之前，先建立一个“对照基线”：在正常情况之下，“文件变大→磁盘使用率上升→删除文件→使用率回落”
>
> 这条链路是完整的。

## 1. 症状

- 我看到了什么：看到了我的电脑
- 怎么发现的：（手动操作 / 监控告警 / 报错）都没有，自己搞的
- 影响是什么：我的电脑，好卡啊

## 2. 环境

- 系统：Ubuntu
- 相关版本： 22.04 LTS
- 时间：2026/11/15

## 3. 排查过程

> 按你实际做的顺序写。**每条命令后面贴原始输出**，哪怕很短。

### 第 1 步：我当时猜是 ______

我跑了：

```
（命令） df -h /(disk free -human-readable /(根目录下))
这个命令常用来快速检查系统根分区还剩多少空间。
```

输出：

```
Filesystem      Size  Used Avail Use% Mounted on
/dev/sdX        40G  3.2G   35G   9% /
```

所以：___这一步是为了快速检查系统根分区还剩下多少空间___（这一步排除了什么 / 确认了什么）

### 第 2 步：接着我猜是 ______

我跑了：

```
（命令） df -h / | tail -1
fallocate -l 2G /tmp/hog.img
df -h / | tail -1
```

输出：

```
（原样贴进来）df -h / | tail -1
/dev/sdX        40G  5.2G   33G  13% /
```

所以：___写入了2G的文件，___

### 第 3 步：定位到了

```
（决定性证据，一贴就破案的那种）
ls -lh /tmp/hog.img
-rw-r--r-- 1 username username 2.0G Nov 15 /tmp/hog.img
tips：如果不加入h这个的话写出来的是字节
```

## 4. 修复

我做了什么：

```
（命令）rm -f /tmp/hog.img
```

怎么确认修好了：

```
（验证命令 + 输出）df -h / | tail -1
/dev/sdX        40G  3.2G   35G   9% /
删除后使用量立即回落，与基线一致
```

## 5. 根因

> 用自己的话写：为什么会出现这个问题？不要写「因为文件被占用了」这种结论，要写机制。

为什么会出现这个问题，我认为就是学习简单的Linux运维排查，关于文件的“文件变大→磁盘使用率上升→删除文件→使用率回落”，最基础的操作吧
